This repository contains the full experiment pipeline for measuring and attributing energy consumption to individual HTTP requests in a distributed microservice system deployed on Kubernetes. The pipeline collects energy data from Kepler, distributed traces from Jaeger, and implements three attribution methods to assign energy to individual user requests.

## Overview

The experiment evaluates three methods for attributing container-level energy (measured by Kepler) to individual user requests (tracked by OpenTelemetry):

| Method | Description |
|--------|-------------|
| **Temporal Differentiation** | E1 only. Difference in total energy between idle baseline and active load window, divided by request count. |
| **Interval-Duration Attribution** | Main method. For each Prometheus scrape interval, energy is distributed proportionally to active span durations. |
| **Span-Duration Attribution** | Comparison. Assigns energy based purely on individual span durations (known underestimation). |

The target system is the **OpenTelemetry Demo** (a microservice e-commerce application) deployed on Kubernetes, with load generated by Locust.

## Cluster Setup

### 1. Deploy Kepler

Kepler must be running as a DaemonSet and exposing metrics to Prometheus via the metric `kepler_container_cpu_joules_total` (counter, per container, per zone: `package` and `dram`).

Verify Kepler is running:
```bash
kubectl get pods -n kepler
# or wherever Kepler is deployed in your cluster
```

Verify the metric exists in Prometheus:
```bash
curl 'http://localhost:9090/api/v1/label/container_name/values' | python3 -c "
import json,sys
data = json.load(sys.stdin)
print([v for v in data['data'] if 'frontend' in v])
"
```

### 2. Deploy OpenTelemetry Demo

```bash
helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
helm install otel-demo open-telemetry/opentelemetry-demo \
  --namespace <your-namespace> \
  --set components.loadgenerator.enabled=false
```

> The orchestrator manages deployment/teardown automatically. Manual deployment is only needed for initial testing.

### 3. Configure Telemetry Settings

The experiment uses three telemetry configurations (managed automatically by the orchestrator):

| Setting | Fine (E1–E4) | Medium (E5) | Coarse (E6) |
|---------|-------------|-------------|-------------|
| Prometheus scrape interval | 1s | 10s | 60s |
| OTel trace sampling rate | 100% | 50% | 1% |

The orchestrator patches these via `kubectl patch` on the ConfigMaps before each experiment run.

## Experiment Design

### E1 — Isolated Requests (Baseline)

Single user actions executed in isolation with a warm system and pre/post baseline measurement. Used to establish ground truth per-request energy.

- **Actions:** Browse, Add to Cart, View Cart, Checkout
- **Request counts (N):** 1, 10, 100, 1000
- **Telemetry:** Fine (1s scrape, 100% sampling)
- **Runs per configuration:** 3
- **Total E1 runs:** 4 actions × 4 N-values × 3 runs = **48 runs**

### E2–E6 — Concurrent Workloads

Mixed concurrent load generated by Locust simulating realistic user behaviour.

| Experiment | Users | Telemetry | Description |
|------------|-------|-----------|-------------|
| E2 | 2 | Fine (1s/100%) | Very low concurrency |
| E3 | 10 | Fine (1s/100%) | Medium concurrency |
| E4 | 50 | Fine (1s/100%) | High concurrency |
| E5 | 10 | Medium (10s/50%) | Reduced telemetry |
| E6 | 10 | Coarse (60s/1%) | Minimal telemetry |

- **Load duration:** 600s per run
- **Runs per experiment:** 3
- **Total concurrent runs:** 5 × 3 = **15 runs**

### Locust Task Weights (approximate distribution)

The Locust file configures the following user action frequencies:
- Browse product catalog: ~60%
- Add to Cart: ~15%
- View Cart: ~15%
- Checkout: ~10%

## Running the Pipeline

### Step 0 — Run All Experiments (63 total runs, ~8 hours)

```bash
# Preview what will run (dry run)
python3 run_all_experiments.py --dry-run

# Run everything
python3 run_all_experiments.py

# Resume after interruption
python3 run_all_experiments.py --skip-completed

# Run only specific experiments
python3 run_all_experiments.py --experiments E3 E5 E6
```

Each run automatically:
1. Redeploys the OTel Demo with the correct telemetry configuration
2. Measures a 120s pre-baseline
3. Runs the load generator
4. Measures a post-baseline (waits for system to stabilise)
5. Collects Kepler metrics from Prometheus
6. Collects traces from Jaeger
7. For E3/E5/E6: collects telemetry infrastructure overhead via `increase()` query

### Step 1 — Preprocessing

```bash
python3 batch_preprocess_all.py
```

For each raw experiment directory, this:
- Parses raw traces and builds a span dependency graph
- Classifies each trace into a user action (browse / add_to_cart / view_cart / checkout / background)
- Injects synthetic spans for uninstrumented infrastructure services (valkey-cart, postgresql, kafka) based on client-side OTel tags
- Aligns Kepler energy intervals with span timestamps
- Outputs `graph_structure.json` and `interval_timeseries.json`

### Step 2 — Attribution

```bash
python3 batch_attribution_all.py
```

Runs all three attribution methods. E1 gets all three; E2–E6 get interval-duration and span-duration only (temporal is not applicable to concurrent mixed workloads).

### Step 3 — Generate Plots

```bash
python3 generate_plots.py \
  --attributed-dir attributed_data \
  --cluster-dir cluster_experiments \
  --output-dir plots
```

Automatically selects the best run per experiment key (highest attribution rate) and generates ~35 plots.

## Attribution Methods

### Interval-Duration (Main Method)

For each Prometheus scrape interval `[t, t+Δt]`:
1. Compute induced energy: `E_induced = E_total - E_idle_baseline`
2. Find all spans active during this interval (overlap > 0)
3. Distribute energy proportionally: `E_span = E_induced × (overlap_s / total_overlap_s)`

Attribution rate = `E_attributed / E_induced`

Uninstrumented services (kafka, llm, flagd-ui, postgresql, valkey-cart) have no spans → their induced energy is structurally unattributable. This is the **Idle Consumption Problem** and is expected.

### Synthetic Spans

To partially recover attribution for infrastructure services that have no OTel instrumentation, the preprocessor injects synthetic spans based on client-side OTel tags:

```
db.system = "redis"       → synthetic span for valkey-cart
db.system = "postgresql"  → synthetic span for postgresql
messaging.system = "kafka" → synthetic span for kafka
```

### User Action Classification

Traces are classified into user actions in `preprocess_experiment_fixed.py::classify_trace_action()`. Priority order:

1. `checkout` — any span contains "checkout" or "placeorder"
2. `add_to_cart` — cart trace with `user_add_to_cart` op OR `AddItem` span (no `GetCart` alone)
3. `view_cart` — cart trace with `user_view_cart` op OR only `GetCart`, no `AddItem`
4. `browse` — product catalog, recommendation, or frontend root spans
5. `background` — monitoring, infrastructure, unclassifiable

> ⚠️ **Important:** `add_to_cart` traces always contain both `AddItem` AND `GetCart` spans (the cart is read after writing). HTTP method alone is therefore unreliable — the presence of `AddItem` is the definitive signal.

## Troubleshooting

### Low attribution rate (<15%)

- Check if the experiment window is too short relative to the Prometheus scrape interval (E6: 60s intervals mean many intervals have no spans)
- Verify that `kepler_metrics.csv` contains the same service names as the traces

### `user_action = "unknown"` in trace_energies

- Rerun preprocessing with the latest `preprocess_experiment_fixed.py`
- The old preprocessor classified cart actions as `"cart"` (ambiguous). The fixed version distinguishes `add_to_cart` and `view_cart`

### Temporal attribution failing for old runs

- Temporal attribution reads from `cluster_experiments/` directly. If you deleted old raw data, `batch_attribution_all.py` will skip the temporal method for those runs (with a `⚠ skipped` warning, not an error)

### Telemetry overhead showing near-zero values

- Ensure you are using the fixed orchestrator which uses `increase()` queries instead of `last - first` delta on raw counters
- `kepler` and `prometheus-server` run continuously across experiments; `last - first` measures accumulated lifetime energy, not experiment-window energy

### Verify Kepler container names in your cluster

```bash
curl -s 'http://localhost:9090/api/v1/query?query=kepler_container_cpu_joules_total' | \
  python3 -c "
import json, sys
data = json.load(sys.stdin)
names = set(r['metric'].get('container_name','') for r in data['data']['result'])
telemetry = [n for n in names if any(t in n for t in ['kepler','jaeger','prometheus','collector'])]
print('Telemetry containers in Kepler:', sorted(telemetry))
"
```

Update `TELEMETRY_OVERHEAD_CONTAINERS` in the orchestrator accordingly.
